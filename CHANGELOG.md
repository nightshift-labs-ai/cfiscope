# Changelog

Taken from the GitHub release notes. Newest first.

## Unreleased

- **kCFI hashes named by their C function type, from BTF.** A kCFI hash is the low 32 bits of xxHash64 of `_ZTS` + the Itanium-mangled function type (`long (short, int)` -> `_ZTSFlsiE` -> `0x1300e12b`). New `cfiscope/kcfi_types.py` reads BTF (an ELF `.BTF` section, a raw BTF file, or the blob inside a raw kernel `Image`), mangles every `FUNC_PROTO` (functions and function-pointer types such as struct ops members; typedefs resolved, top-level qualifiers of parameters dropped but kept on the return type as Clang does, K&R `()` prototypes mangled without a parameter code, substitutions such as `_ZTSFiP7sk_buffS0_E`) and maps hash -> type and example names. The command line uses the input's own BTF automatically, or `--btf PATH` (`--no-btf` turns it off): `--sites` prints `hash 0x4f4ccb9d (int (struct file *, int))`, `--json` adds `type`, `type_mangled` and `type_examples` per kCFI site, and the summary adds `kCFI hashes named: N of M (x%)`. Without BTF the output is unchanged. On the Android 14 GKI 6.1 `Image` (raw, no symbols) its own BTF names all 4,184 distinct hashes, all 13,897 call sites; 0 hashes got two types; BTF writes 0 elements for both `T []` and GNU `T [0]`, so such an array is mangled `A_` (as Clang does for `[]`) and also entered as `A0_` (the `android_vh_typec_*` hooks take a `u32 (*)[]`); AArch64's `va_list` is mangled `St9__va_list`; the BTF counts (128,248 types, 29,786 prototypes) agree with `bpftool btf dump`. The IDA layer names hashes from the input file's BTF in its disassembly and pseudocode comments (`CFIScope: 3 candidates of int (struct file *, int): ...`) and the candidates list title (fake IDA modules only; no new IDA API names). Tests: one C file built by `zig cc` (clang 22.1.8) for aarch64 kCFI and for bpf BTF; for all 17 functions the BTF-derived hash equals the hash in front of the function; a second such file covers `const`/`volatile` return types and K&R `()` (8 functions). The test suite also runs a 175-function ground-truth corpus built the same way (162 of them in BTF): all 162 hashes, plain and integer-normalized, are in the table; 160 match by direct mangling, the other 2 are K&R `f()` definitions that BTF records like `f(void)`. Kernels built with integer normalization (`CONFIG_CFI_ICALL_NORMALIZE_INTEGERS`, set with Rust support) are covered too: each prototype is also entered under its integer-normalized hash (`long (short, int)` -> `_ZTSFu3i64u3i16u3i32E.normalized` -> `0xe1d7ea79`), labelled `long (short, int) [normalized]`; checked against Clang on a test fixture (17 functions) and the 162-function corpus, and on a real kernel: on the Android 16 GKI 6.12 `Image` (Rust enabled, so integer-normalized) its own BTF names 4,621 of 4,626 distinct hashes (99.8%), 15,964 of 16,164 call sites, all labelled `[normalized]`; the 5 left (200 call sites) are all inside Rust functions of its `core` library (`core::fmt`, `core::error`), whose types BTF does not describe. On the Android 15 GKI 6.6 `Image`: 4,466 of 4,466 (100%), every call site. An anonymous struct or enum reached only through a pointer typedef (`typedef struct {...} X, *PX;`) is named after the first typedef of it that BTF lists (Clang uses the first one declared; BTF keeps use order, so the two can differ). Results are kept per BTF type and depth, and a prototype of more than 4,096 nodes is skipped: a 30-level crafted chain that took over 50 s now takes 0.02 s (large crafted BTF files can still take seconds).
- **The Quick try shows the types too.** The two Quick-try fixtures, `tests/fixtures/x86_64-kernel.o` and `aarch64-kernel.o`, now carry the BTF of `t.c` (built with `zig cc -target bpfel-freestanding-none -g -O2 -c` and copied in with the new `tools/add_btf_section.py`, plain Python), so the command line and the IDA layer name all 21 hashes in them (`long (short, int)` for the call in `do_call_2`). Their code, symbols and scan results are unchanged.

## v0.1.20 (2026-11-16)

- **IDA: answering No to "Create functions" no longer leaves functions behind** (fake IDA modules only). A call cross-reference (`fl_CN`) makes IDA create a function at its target (SDK `xref.hpp`), so Scan, which asked only after adding its cross-references, produced functions at candidates even after No, and Remove annotations did not undo them. Scan now asks first. After No, only a candidate at the start of a function IDA has gets a call cross-reference; a candidate inside one (on x86 IDA may start the function at the `__cfi_` preamble, 16 bytes earlier) gets a user data cross-reference (`dr_O`) instead, and a candidate IDA has no function for gets none (`data_xrefs_inside_function` and `xrefs_skipped_no_function` in Scan's result). `xref.hpp` notes function creation for `fl_CF` and `fl_CN` only, and `ida.hpp`'s `AF_PROCPTR` makes functions for data cross-references from data, while this one comes from an instruction; that it creates no function is assumed, not checked in IDA. A later Scan replaces a cross-reference of the other kind, so each call and candidate pair keeps one; Remove annotations deletes both kinds, and CFIScope's own data cross-references never mark a candidate "address taken". On the 6.1 kernel in the fake modules of `tools/showcase_ida_stub.py` (its new `--no` answers No), No gives 44,695 call and 23 data cross-references (8 candidates), Yes 44,718 call cross-references. `tools/cfiscope_headless.py` does the same without `--define-functions`. Cancel (or Esc) on that question stops the scan before anything is written. With `--no-analysis` IDA's auto-analysis, which creates the functions, does not run, so a fresh kernel file may have no functions yet; the README and the option's help say to add `--define-functions` to get cross-references. Functions created after Yes stay after Remove annotations; the `functions created` count after Yes leaves out any function IDA may make from a call cross-reference at a candidate inside another function.
- **IDA: Scan offers to wait for auto-analysis** (fake IDA modules only). During analysis, a candidate in bytes IDA has not classified yet passes the data check, and data references IDA has not found yet are missing; Scan now asks first (`ida_auto.auto_is_ok`): Yes waits (`auto_wait`, which its Cancel button stops, and then nothing is scanned), No scans now, Cancel does nothing. With auto-analysis turned off (`ida_ida.inf_is_auto_enabled`, Options > General > Analysis), whose queues then never empty, Scan does not ask and scans at once. IDA API names: 88 checked against the official stubs, 0 missing; 70 `ida_*` names in the stubs of IDA 9.1 to 9.5.
- **IDA: no dead Cancel button while Scan works** (fake IDA modules only). The scan's wait boxes showed a Cancel button that nothing checked; they now hide it (`HIDECANCEL`), and "Create functions" runs inside one too. If IDAPython's own "Running Python script" box is cancelled, the Output window says `interrupted: the action stopped part-way; run it again (Scan kCFI calls or Remove annotations) to finish` (for Remove annotations too) instead of showing a traceback.

## v0.1.17 (2026-11-12)

- **Linux 5.x jump-table CFI on aarch64 (Android 12/13 GKI).** When an aarch64 image has no kCFI checks but has a CFI jump table (the longest run of 8-byte `bti c; b <function>` entries), CFIScope reads the older Clang CFI: range checks (`sub; ror #3; cmp; b.hs/b.hi/b.lo/b.ls`, count as an immediate or in a register, also hoisted out of loops), single-member checks (`cmp; b.ne`) and calls checked only by `__cfi_slowpath(_diag)`. The base register is traced back through `adrp`/`add` and `mov` copies; candidates are the branch targets of the entries the check accepts. Each site gets a kind (`range`, `single`, `slowpath`), the 64-bit type id from its slow path and, with `__typeid_<type>_global_addr` symbols, the demangled type (`int (file*, int)`). Hand-decoded, no new dependency.
- Same IDA actions, comments (`jtCFI <type>: ...`), cross-references, lists and pseudocode comments as for kCFI. In IDA the type names come from the database's names and, since IDA keeps one name per address and these share theirs with `foo.cfi_jt` entries, from the input ELF's symbol table when that file is still on disk. Command line: summary, `--sites`, `--callers`, `--targets` and `--json` (new fields `kind`, `type_id`, `type`, `type_mangled`, `jump_table_range`, `note`, `range_from`, `other_checks`; `hash` is the 64-bit id). kCFI output is unchanged.
- Measured on gki-certified-boot-android13-5.15-2024-01_r1 with `tools/eval_gki_oldcfi.py`: 14,052 of 21,738 `blr` in kernel text get candidates (64.6%), median 6 per call; all 24,976 distinct candidates start at a kallsyms function; every check with candidates whose range was read at the check and whose slow path passes a type id starts at that type's `__typeid` symbol (10,890 range, 2,041 single; 1,036 range and 105 single checks copy their range from another check of the same type id and are reported apart, with `range_from` in `--json`). Module targets are not listed; tracepoint and vendor-hook calls carry no CFI check. The eval tool also splits the 7,686 unresolved `blr`: 1,950 linked to a check without in-image candidates, 1,537 in tracepoint/vendor-hook iterators, 1,015 the CFI runtime's own calls into `__cfi_check` (inlined slow paths; leaving these out, 14,052 of 20,723 = 67.8% get candidates), 2,030 inlined tracepoint loops elsewhere, 225 with a `ror #3` or slow-path call just before them (likely undecoded checks), 929 with none of these (pattern matches, not decoding).
- In IDA, "Candidates for this call" on a call or check always picks that site, even where jump-table CFI spans from check to call overlap (GKI 5.15: 0 of 16,003 calls pick another call's list), and "Callers of this function" on a `foo.cfi_jt` jump-table entry, where pointers to `foo` point, answers for `foo`.
- Candidate lists for jump-table CFI mark a candidate "address taken" (and list it first) when its `foo.cfi_jt` entry is referenced as data, since that is where pointers to `foo` point in such kernels.
- A `cmp; b.ne` against one jump-table entry with no CFI slow path behind it is an ordinary function-pointer comparison and is not reported as a check (3 such sites plus one inside `__cfi_check` on GKI 5.15). The summary line "checks named from __typeid symbols" (JSON `named_checks`) counts checks, not types.
- Also measured, with no code change, on Android 12 GKI android12-5.10-2024-01_r1: 14,136 of 20,939 `blr` get candidates (67.5%), median 6, all 23,399 candidates exact function starts; its kallsyms keeps only one `__typeid` name (it names 27 checks), so almost all types show as ids.

## v0.1.15 (2026-11-11)

- **Candidates in Hex-Rays pseudocode.** After a scan, a decompiler hook (`Hexrays_Hooks.func_printed`) appends a comment such as `// CFIScope: 3 candidates: impl_2_0, impl_2_1, impl_2_2` to the pseudocode line of each kCFI call site in the function being printed: at most 5 names, then "and N more"; a site without candidates gets "CFIScope: 0 candidates in this image". The line is found with `cfunc.get_eamap()` (call address to statements) and `cfunc.find_item_coords()`. The hook reuses the scan results, never scans, and only changes the printed text: nothing new is stored in the database. Remove annotations turns the comments off; Scan and Remove annotations flush the decompiler cache (`clear_cached_cfuncs`) so that the next decompile shows the change.
- The hook is installed only if `ida_hexrays` imports and `init_hexrays_plugin()` returns true (tried when the plugin loads and again at each Scan that finds call sites), and it is removed when the plugin unloads. An exception inside it is caught, reported once in the Output window, and the hook returns 0. Without the decompiler, CFIScope works as before.
