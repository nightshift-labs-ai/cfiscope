# How CFIScope works

The short version is in the [README](../README.md). This page has the full description of each action, what a candidate is, the supported targets, the fixture objects, the command line and the headless runner. Measurements are in [VERIFICATION.md](VERIFICATION.md); the Linux 5.x jump-table CFI is in [JTCFI.md](JTCFI.md).

## Why it matters

Kernel attack surface runs through function pointers: `file_operations`, `net_device_ops`, tracepoints, callbacks. In a stripped binary every one of those calls is a dead end for static analysis, and tracing them by hand or with a debugger is slow, and impossible on a kernel you only have as a file. kCFI happens to record the answer, because the compiler must know which types may be called, and CFIScope turns that record into cross-references you can follow.

## The actions in full

- **Scan kCFI calls** (`Alt-Shift-K`): finds every check, comments the call site with the type hash and candidate count, adds cross-references when the candidate list is short (at most 16), or, in a longer list, to the candidates stored at the offset of the call's struct member when those are at most 16 (new in 0.1.23; not to those found by array stride only; see [below](#candidates-stored-in-a-matching-slot)), and offers to create functions at candidates IDA has not recognised. It asks before adding any cross-reference, because a call cross-reference makes IDA create a function at its target. If you answer No, only a candidate at the start of a function IDA has gets a call cross-reference; a candidate inside one (on x86 IDA may start the function at the `__cfi_` preamble, 16 bytes earlier) gets a data cross-reference instead, so you can still go between the call and the candidate (the IDA SDK says a call cross-reference creates a function; of data cross-references it says so only for those from data, under the analysis option `AF_PROCPTR`, and this one comes from an instruction; that it creates no function is assumed, not checked in IDA), and a candidate IDA has no function for gets none. Scan's result in the Output window counts these two (`N of them data cross-references to candidates inside a function`, `none to N candidates that have no function`); Cancel stops the scan before anything is written. If IDA's auto-analysis is still running, it first offers to wait for it. Your own comments are kept. No cross-reference or function is made at a candidate that IDA holds as data (or inside another item) or that lies outside the code segments, and when the database or the input ELF names the kernel's text bounds (in practice the input ELF must still be at its path: IDA keeps one name per address, so a database alone usually lacks some of these names, and then nothing is left out), candidates in `.rodata` and data (between `_etext` and `_sinittext`, outside the code areas named there) are left out as on the [command line](#without-ida-scripts-other-tools-ci); the Output window counts both (tested on fake IDA modules only). That result is one sentence, for example on the Quick-try fixture `Scan: 21 kCFI call sites (21 types, all named from the file's BTF); 21 with candidates (median 3); 21 comments and 76 cross-references added. Next: Alt-Shift-T on a call, Alt-Shift-X on a function.` (after Yes; checked against fake IDA modules only). Start IDA with the environment variable `CFISCOPE_DEBUG=1` to also get the raw counts as two JSON lines, as Scan printed them before 0.1.23.
- **Candidates for this call** (`Alt-Shift-T`): a jump list of every function the call under the cursor may reach (same CFI type). If the cursor is not on a kCFI check or its call, the nearest check in the same function is used; the list's title names the call address it chose. In a pseudocode window (with the Hex-Rays decompiler) there is no such guess: it takes the scanned call(s) that the decompiler prints on the cursor's line, the line that carries the CFIScope comment (`ida_hexrays.get_widget_vdui`, the line number `cpos.lnnum`, and the function's address map `get_eamap` with `find_item_coords`); if the line has several, a small modal list asks which one. On a line with none (a call the decompiler splits over several lines, the cursor on an argument's line) it takes a call or check exactly at the cursor's address, still with no guess, and otherwise warns. Without the decompiler, or when IDA gives no pseudocode view, it works as in disassembly. That `find_item_coords` and `cpos.lnnum` count lines the same way is assumed, not checked in IDA (tested on fake modules only).
- **Callers of this function** (`Alt-Shift-X`): every indirect call site that may reach this function (same CFI type). With struct members (new in 0.1.23), the calls whose member slot holds the function come first (at the member's offset, then by array stride), each in scan order, and the row's note ends with `stored in a proto.sendmsg slot`, `by array stride` or `same type only` (`core.callee_slot()`; `--callers` ends its lines with `[tcp_sendmsg: ...]` and gives `callee_slot_backed` in `--json`). IDA's own xrefs window shows such a call only after Scan, and only when its list has at most 16 candidates or the function is one of at most 16 stored at the offset of the call's member (Scan adds cross-references to those only); this list also works before Scan and includes the other calls. In a pseudocode window the function is the decompiled one (`cfunc.entry_ea`), wherever the cursor is in it. Only calls are counted: with the Linux 5.x jump-table CFI, a check whose call was not linked comes after the calls as a type check only, and the CFI runtime's own checks (in `__cfi_check`, which guard no call) are left out.
- **Functions of this type** (new in 0.1.24; no default key): a non-modal jump list of every function with the kCFI type hash of the function under the cursor (in pseudocode, the decompiled function), whether or not a call site checks that hash: the command line's `--implements` with that function's name ([below](#functions-of-a-type)). The hash is the word in front of the start of IDA's function holding the cursor, taken as `--implements NAME` takes it; failing that, one a check or BTF knows in front of the cursor's address, of a scanned candidate inside the function, or, on x86-64, of the entry after a `__cfi_` preamble that IDA made the function's start. The title gives the hash and its C type from BTF; each row notes `this function` and `address taken` (IDA has a data reference to it). Before any Scan it runs the same read-only scan the other lookups run; it writes nothing. It warns instead for the jump-table CFI, for aarch64 code whose indirect calls no check guards, for x86-64 with no check, and for a function with no hash in front of it. Checked against fake IDA modules only, not checked in IDA.
- **List kCFI call sites** (new in 0.1.23): a non-modal window of every call site the scan found, which Scan also opens at its end (with no site it shows nothing; Scan's warning says why). Columns: Address (the call, or the check when no call was linked), Function+off, Member (the BTF member of the call's type at the offset the call loads its pointer from; a match, not proof, see [below](#naming-the-struct-member-a-call-loads-its-pointer-from-aarch64); empty when there is none), Type (the C prototype when BTF named the hash, else `hash 0x...`; with the jump-table CFI, the type the check names), Candidates (column format `CHCOL_DEC`, decimal number, so that IDA can sort it as a number; not checked in IDA) and First candidates (the names of the call's comment: the first six, address-taken first, then `+N more`, or why there are none; with candidates stored in a slot of the call's member, `in a proto_ops.sendmsg_locked slot: tcp_sendmsg_locked; same type only: 10 more`, see [below](#candidates-stored-in-a-matching-slot)). Enter jumps to the call (tested on fake IDA modules only). These are the fields of each `python3 -m cfiscope FILE --sites` line. Before any Scan it runs the same read-only scan the lookups run and writes nothing. A window left open from an earlier scan is closed first (`close_chooser`); opening the list again for the same scan shows the same chooser object again (IDAPython tells choosers apart by their Python object; how IDA handles this was not checked in IDA). The rows are a snapshot of the scan: the Function+off column and the order of the names come from what IDA has analysed when the list is built, so after a Scan made before auto-analysis finished, run Scan again to refresh them. The rows are built at once, behind a wait box: 0.09 to 0.15 s for the 13,897 sites of GKI 6.1 through the fake IDA modules of `tools/showcase_ida_stub.py --list` (see [VERIFICATION](VERIFICATION.md#the-call-site-list)); not measured in IDA.
- **Remove annotations**: removes the comments and cross-references the scan added, and turns the pseudocode comments off. On a list of at most 16 it deletes any call or data cross-reference from the call to a candidate; on a longer one only those to the candidates Scan gives cross-references (`xref_targets()`, new in 0.1.23), so one you added to another candidate stays, and so do Scan's own when this scan cannot read the slots (the input file moved since). Functions created when you answered Yes stay, including any IDA makes itself from a call cross-reference. The Output window's `functions created` counts only those CFIScope made: after Yes, a candidate inside another function gets a call cross-reference and no `add_func`, so a function IDA may make there is not counted.
- **Pseudocode comments** (with the Hex-Rays decompiler): after a scan, the pseudocode line of each kCFI call gets a trailing comment such as `// CFIScope: 3 candidates of long (short, int): impl_2_0, impl_2_1, impl_2_2` (at most 5 names, then "and N more"), with the struct member first when it is known: `// CFIScope: proto_ops.sendmsg, 14 candidates of int (struct socket *, ...): ...`. The line is found through the decompiler's address map when a function is printed; the comment is display text only, nothing is saved in the database (only the scan marker below). Not yet run in IDA and not tested with the real decompiler, only against a fake `ida_hexrays` module.
- **After reopening a database** (new in 0.1.23): Scan stores a marker in the netnode `$ cfiscope` (a digest of the segment bounds and your answer to "Create functions", which becomes the default the next time Scan asks); `tools/cfiscope_headless.py` stores it too. When a database with the marker is opened again, the first function the decompiler prints, or the first Candidates/Callers lookup, re-runs the read-only scan (the same one a lookup runs) so the pseudocode comments and lookups work without Scan. When that is the first decompile, it runs the scan once, without a wait box: about 2 s on a GKI 6.1 kernel (measured with the command-line tool), so the first pseudocode window opens that much later. This restore asks nothing and writes nothing (no comments, cross-references or functions), waits while auto-analysis is running, and on any error prints one message (with the traceback) in the Output window, on an interrupt one line, and leaves the comments off. If the segments changed since the scan (a rebase), it does not restore and says to run Scan again. Remove annotations deletes the marker. Tested only against fake `ida_netnode` and `ida_hexrays` modules.

All six actions are under Edit > Plugins. Scan, the three lookups and the call-site list are also on the right-click menu of disassembly and pseudocode views (CFIScope submenu). The default keys `Alt-Shift-K`, `Alt-Shift-T` and `Alt-Shift-X` (X as in cross-references) replace `Ctrl-Alt-K` (Keypatch's key), `Ctrl-Alt-T` (a terminal on GNOME and Ubuntu, so IDA never saw it) and `Ctrl-Alt-C` of earlier versions; they are not among IDA 9's published default shortcuts (docs.hex-rays.com, Shortcuts) or the window-manager keys of GNOME 46 (`org.gnome.desktop.wm.keybindings`), but that page lists the common shortcuts only, and another plugin may still use them. Rebind them in Options > Shortcuts.

## What a candidate is

Candidates are type-compatible functions: kCFI proves a function has the right type hash, not that a given call ever reaches it. Most lists are short (median 6 candidates per call that has any, on each of the four GKI kernels in [VERIFICATION.md](VERIFICATION.md#kcfi-on-real-kernels)), but a few common types have hundreds or more (the largest lists have 1,458 to 1,812). Treat a long list as a type filter and a short one as a strong lead. For a call with a struct member, the candidates stored in a slot of that member come first ([below](#candidates-stored-in-a-matching-slot)).

## Naming a hash by its C type

Clang computes a kCFI hash as the low 32 bits of xxHash64 of `_ZTS` followed by the Itanium mangling of the function type: `long (short, int)` is `_ZTSFlsiE`, hash `0x1300e12b`; `int (struct sk_buff *, const char *, void (*)(int))` is `_ZTSFiP7sk_buffPKcPFviEE`, hash `0x2c94c37f`. The hash cannot be reversed, but a kernel built with `CONFIG_DEBUG_INFO_BTF` carries every function prototype and every function-pointer type in its BTF, so `cfiscope/kcfi_types.py` mangles each BTF `FUNC_PROTO` the way Clang does (typedefs resolved, top-level qualifiers of parameters dropped but kept on the return type, arrays and functions decayed to pointers, K&R `()` mangled with no parameter code (BTF writes `long f()` exactly like `long f(void)`, so a function with an empty prototype is entered under both hashes, the K&R one without example names), typedef-named anonymous structs by the typedef name, Itanium substitutions such as `S0_`) and looks the hashes up. It reads BTF from an ELF `.BTF` section, a raw BTF file, or the blob inside a raw `Image`; a module's split BTF is refused (it needs vmlinux's BTF). On the GKI 6.1 kernel of the walkthrough, the raw `Image`'s own BTF (29,786 prototypes) names all 4,184 of its distinct call-site hashes, with no hash given two types; AArch64's `va_list` is `std::__va_list` (`St9__va_list`). BTF writes 0 elements for both `T []` and GNU `T [0]`; such an array is mangled `A_`, as Clang does for `[]`, and also entered as `A0_` (two `__traceiter_android_vh_typec_*` vendor hooks call through a `u32 (*)[]` prototype). On GKI 6.6 all 4,466 are named, on GKI 6.12 4,621 of 4,626 (see below). The tests check the mangling against Clang itself: one C file built by `zig cc` both with `-fsanitize=kcfi` for aarch64 and as bpf with BTF, where all 17 functions' BTF-derived hashes equal the hashes in front of them, and a second one for `const`/`volatile` return types and K&R `()` (8 functions). Kernels built with integer normalization (`CONFIG_CFI_ICALL_NORMALIZE_INTEGERS`, set with Rust support) are covered too: each prototype is also entered under its integer-normalized hash (`long (short, int)` -> `_ZTSFu3i64u3i16u3i32E.normalized` -> `0xe1d7ea79`), labelled `long (short, int) [normalized]`; checked against Clang on a test fixture (17 functions) and the 162-function corpus, and on the Android 16 GKI 6.12 kernel (Rust enabled): its own BTF names 4,621 of 4,626 hashes, all through their normalized form; the 5 left (200 call sites) are all inside Rust functions of its `core` library (`core::fmt`, `core::error`), whose types BTF does not describe. Plain `char` is normalized as unsigned unless the BTF marks it signed: pahole leaves plain `char` unmarked (newer pahole marks `signed char`, as in the GKI 6.6 and 6.12 BTF; GKI 6.1's leaves both unmarked), and every kernel since Linux 6.2 is built with `-funsigned-char` (integer normalization came later), so this holds on x86-64 too, though only aarch64 kernels were measured.

## Naming the struct member a call loads its pointer from (aarch64)

New in 0.1.23. `sock->ops->sendmsg(sock, msg, len)` compiles to a load of the pointer from byte 136 of `struct proto_ops` (`ldr x8, [x8, #136]` on GKI 6.1), the kCFI check of `x8` and `blr x8`. `cfiscope/core.py` (`member_offsets()`) walks back from the check to that load and reads its immediate offset. `cfiscope/kcfi_types.py` (`member_slots()`, built with the hash table above) maps every function-pointer member in BTF to (its prototype's kCFI hash, its byte offset), including members of embedded and anonymous structs and unions and of short arrays, named after the struct that declares them. A call whose (hash, offset) has exactly one member gets that name: in the command line's lines (`call proto_ops.sendmsg hash 0x1ebda935 ...`), `--json` (`member`, `members`, `member_offset`), the IDA comment (`kCFI proto_ops.sendmsg 0x1EBDA935 ...`), the pseudocode comment, the Candidates title, the Callers rows and the call-site list. With several, all are shown as `one of N members (a, b, c, +K more)` and `member` is `null` in JSON; none is picked. A call whose load is not decoded, or whose offset matches no member, prints exactly what it printed before.

The walk is straight-line and gives up: on a stack base, an `adrp` base on the path it walked back (an `adrp` further back or behind a branch is not seen), `ldp`, register offsets, writeback, a call that clobbers the register, or a branch landing between the load and the check. The name says only that BTF has one member of that type at that offset; a pointer to a lone function pointer (`(*pp)()`, offset 0) reads the same as a struct's first member, and a pointer the compiler has already moved into the struct is read from the wrong origin (`gic_enable_of_quirks+0x54` on GKI 6.6 and 6.12 loads `gic_quirk.init` through a pointer to it, at `[x22, #0]`, and is named `vhost_task.fn`). x86-64 is not read yet. Counts on GKI 6.1, 6.6 and 6.12, the cost (about 0.4 s in the member map and the walk; a whole `--callers` command on GKI 6.1 took 0.5 to 0.8 s longer) and what the tests check: [VERIFICATION](VERIFICATION.md#struct-members-aarch64).

## Candidates stored in a matching slot

New in 0.1.23; aarch64, for calls with a struct member (above). An ops table is a static object: `inet_stream_ops` holds `tcp_sendmsg_locked` at byte 216, its `sendmsg_locked` member. `cli.slot_offsets()` reads every 8-aligned word of a linked image's loaded segments (for a `.o` or `.ko`, its 64-bit absolute relocations into allocated data sections, which point at a function where the command line lays the code out) and keeps the words that hold a candidate's address, each with the object it lies in and its offset there: the nearest `FUNC` or `OBJECT` symbol at or below it, when that one is an object (inside its size when the symbol has one; kallsyms gives none, so a word is charged to whatever object lies below it). `kcfi_types.rank_slots()` marks a candidate slot-backed for a call in two ways:
- **at the member's offset:** one of its words is at the member offset the call loads, in some object;
- **by array stride** (weaker, listed after those): a word is at that offset modulo the size of a struct that has such a member there, and the same object holds another candidate of the call at an offset congruent to it, as an array of those structs does. One such word proves nothing (review s197: on GKI 6.1, `sock_diag_rcv` sits at byte 592 of the object below it, `bpf_sk_lookup_assign_proto`, and 592 is 96, `sk_buff.destructor`, modulo 248; it is a `netlink_kernel_cfg.input` initializer). A struct of 16 bytes or less is not used: every 8-aligned word, or every other one, would match it, and an ops table with many members of one type, such as a `dev_pm_ops`, passes for an array of them. So in an array of structs of 16 bytes or less only the first element counts (at the member's offset), and an array embedded in another object at an offset that is not a multiple of its stride is not matched.

`core.slot_first()` puts the candidates at the member's offset first, then those by array stride, then the rest, each group in its previous order; nothing is removed. A one-line list (`--sites`, `--callers`, the IDA comment, pseudocode comment and call-site list) names every candidate in its group when the list fits the limit (`2 candidate(s): in a a_ops.send slot: send_x; same type only: send_y`), and when it is longer, names up to the limit of the slot-backed ones and counts the rest of each group (`11 candidate(s): in a proto_ops.sendmsg_locked slot: tcp_sendmsg_locked; same type only: 10 more`, `core.slot_text()`). `--targets` lists the groups in full under the headers `in a proto_ops.sendmsg slot:`, `by array stride:` and `same type only:`, and `--json` gives each candidate `slot_backed`: `offset`, `stride` or false (only when the ranking ran: not with `--raw`, which has no symbols; its summary says so). `--callers` lists the calls whose member slot holds the function first and ends each line with `[tcp_sendmsg: in a proto.sendmsg slot]`, `[...: by array stride]` or `[...: same type only]` (`callee_slot_backed` in `--json`). In IDA, `ranked()` puts the two slot groups before the address-taken candidates, the Candidates window notes `stored in a proto_ops.sendmsg_locked slot` or `by array stride`, Callers orders and notes its rows the same way, and Scan's 16-cross-reference cap counts the candidates at the member's offset first: a longer list gets cross-references to those when there are at most 16 (never to those found by array stride only). The plugin reads the slots from the input file, so only when it is still at its path and the database has its addresses (each of its code ranges starts with the same bytes at the same address; not checked in IDA); when the file is there but not an ELF or not at those addresses, Scan says in the Output window that it skipped the ranking.

What a slot says: the image stores that function where the call's member sits in some object. It is evidence, not proof: the object may be another struct type with a member of the same type at that offset, an array matched by stride may hold another struct of the same size, and a pointer set at run time or stored in a module's table is in no slot of the image, so those candidates stay in the list, after the others. Counts on GKI 6.1, 6.6 and 6.12 and the cost: [VERIFICATION](VERIFICATION.md#candidates-stored-in-a-matching-slot).

## Functions of a type

New in 0.1.24; the IDA side checked against fake IDA modules only, not checked in IDA. `--implements SPEC` turns SPEC into one kCFI hash and lists every function with that hash in front of it, whether or not a call site checks it. A struct member (`file_operations.unlocked_ioctl`, `outer.inner.notify`, members of anonymous structs and unions by their name) is looked up in BTF (`kcfi_types.member_candidates()`): its type must be a pointer, or an array of pointers, to a `FUNC_PROTO`, which is mangled and hashed as [above](#naming-a-hash-by-its-c-type), plainly or integer-normalized as the input's call sites are. A C type is matched against the C text of the BTF prototypes (spacing aside), a `_ZTS...` name is hashed, a hash is taken as it is, and a function's name gives the hash in front of that function (`core.function_hash()`). When SPEC gives several hashes that functions carry, it refuses: give the hash. The functions are the candidate list of a call site that checks the hash, else the scan that finds candidates (`core.implementations()`): every occurrence of the hash in the code (an aligned word on aarch64, the `imm32` of `mov r32, imm32` on x86-64) at the offset the input's checks use, followed by what looks like a function entry, within the kernel text bounds the candidates use. On GKI 6.1, `file_operations.unlocked_ioctl` gives 136 functions, the same set as the `FUNC` symbols with `0xe01408cd` in the word before them. For a function's name, the word in front of it counts when a check or BTF knows it, or when only patchable-entry NOPs (0x90 on x86-64, `nop` or another hint on aarch64) stand between it and the function and, on aarch64, it does not decode as `ret`, `b`, `bl`, `br`/`blr`, `brk`, a hint, `udf`, a system instruction (`msr`, `mrs`, `isb` and the other barriers, `sys`), `eret`, `drps`, `svc`, `hvc` or `smc`, which is what usually stands in front of a function with no hash (on GKI 6.1, 9,405 of the 9,431 words in front of a named function that BTF does not name as a type). The form can still be wrong both ways: a real hash that decodes as such an instruction is missed without BTF unless a call site checks it (on GKI 6.1, 592 of the 48,021 that BTF names: 2,257 decode so, and 1,665 of those are checked), and an instruction word or a literal of another encoding passes; so a hash taken by its form alone is refused when it also stands in front of an address that is not the start of a function symbol (in IDA: of a function of the database), as it does for GKI 6.1's `init_kernel_el` (0xffffffc0, the high half of a pointer). A module's member or C type needs `--btf` with its kernel, whose BTF the module's split BTF continues (a hash needs none), and `--with vmlinux` adds the kernel's functions of that hash. Limits: the hash says a function has the member's type, not that anything stores it there (`file_operations.compat_ioctl` gives the same 136, and `memfd_fcntl` and `pipe_fcntl` are not ioctl handlers); a function with no hash in front of it (a static one whose address is never taken: 19 of GKI 6.1's 261 functions named `*_ioctl`) is not listed; with no check and no indirect call in the input, aarch64 is read at -4; aarch64 code whose indirect calls no check guards, and x86-64 with no check, are refused, as is the jump-table CFI; without `--with` a module lists only its own functions; and two types can share a 32-bit hash (the header then names both).

## Supported targets

Supported targets: aarch64 and x86-64 kernels built by Clang with kCFI (`CONFIG_CFI_CLANG` on Linux 6.1 or later), for example Android GKI android14-6.1 and later. Since v0.1.17 also aarch64 kernels built with the older jump-table CFI of Linux 5.x, measured on an Android 12 GKI 5.10 and an Android 13 GKI 5.15 kernel (see [Linux 5.x jump-table CFI](JTCFI.md) for what it reads and what it does not). Loadable modules (`.ko`) are read as they are (new in 0.1.23; measured on three GKI android14-6.1 modules, see [VERIFICATION](VERIFICATION.md#loadable-modules-ko)): a module's lists hold its own functions; the command line's `--with vmlinux` adds the kernel's functions of each call's type, and `--btf` with the module's kernel reads the module's split BTF on top of the kernel's. Not supported: GCC-built kernels (most desktop distribution kernels have no kCFI checks to read) and x86-64 kernels with the jump-table CFI; on those the scan finds 0 sites and says so. The scanner was scored on a real Android GKI kernel for each architecture (numbers in [VERIFICATION.md](VERIFICATION.md)); the IDA layer has not been run in IDA yet (see [Status](../README.md#status)).

## The fixture objects

Quick try, no download (about a minute): the repository ships small objects built with Clang kCFI from `tests/fixtures/t.c`, with the known answer for every call in `tests/fixtures/truth.json`: the generator wrote each function-pointer type and its implementations into `t.c`, and Clang built the objects.

The same scan from the command line, real output:

```
$ python3 -m cfiscope tests/fixtures/x86_64-kernel.o --sites --max-list 4
0x108033  do_call_0+0x13  jump hash 0x7230bf2a (long long (void))  4 candidate(s): impl_0_0, impl_0_1, impl_0_2, impl_0_3
0x116033  do_call_1+0x13  jump hash 0x36b1c5a6 (int (void))  6 candidate(s): impl_1_0, impl_1_1, impl_1_2, impl_1_3 ...
0x11e03a  do_call_2+0x1a  jump hash 0x1300e12b (long (short, int))  3 candidate(s): impl_2_0, impl_2_1, impl_2_2
...
```

(Spacing condensed. Addresses are where the command-line tool lays out the object's sections; IDA will place them elsewhere. The types in brackets come from the BTF of `t.c` that the two `*-kernel.o` fixtures carry, added with `tools/add_btf_section.py`.)

## Without IDA (scripts, other tools, CI)

The scanner is plain Python 3 with no dependencies, so the same answers are available from the command line, for example to feed another disassembler or a pipeline:

```
python3 -m cfiscope vmlinux                         # summary
python3 -m cfiscope vmlinux --sites                 # every call site and its candidates
python3 -m cfiscope vmlinux --callers tcp_sendmsg   # indirect calls that may reach a function (same kCFI type)
python3 -m cfiscope vmlinux --targets 0xffffffc008cc55ac
python3 -m cfiscope vmlinux --implements file_operations.unlocked_ioctl   # every function of that member's type
python3 -m cfiscope Image --raw --arch aarch64 --base 0xffffffc008000000
python3 -m cfiscope foo.ko --sites --with vmlinux   # a module: also the kernel's functions of each call's type
```

Run it from the repository root or the installed plugin folder (the folder that holds `cfiscope/`; after `hcli plugin install`, `~/.idapro/plugins/cfiscope` on Linux and macOS), or by path from any folder: `python3 <that folder>/cfiscope vmlinux` (new in 0.1.23; before, this stopped with `ImportError: attempted relative import with no known parent package`). Input is a 64-bit ELF (a `vmlinux`, a kernel with symbols restored by vmlinux-to-elf, or a `.o`/`.ko`) or, with `--raw`, a bare kernel image. Symbols are used to print names and, when the ELF names `_stext`, `_etext`, `_sinittext` and `_einittext` (a `vmlinux` with its symbols, or the output of vmlinux-to-elf), to leave out kCFI candidates outside kernel code: on aarch64 the type hash in front of a function is a bare 32-bit word, and the same value can occur in `.rodata`. Only candidates between `_etext` and `_sinittext` are left out (`.rodata` lies there, and on x86-64 also `.data`), except in the code areas that arm64 names there: its idmap code since 6.6, the entry trampoline, hibernate and kexec code. Everything before `_etext` and from `_sinittext` on, init and exit text included, is kept, and if one of those code areas is named at one end only, nothing is left out. Without those four symbols (`--raw`, a stripped `vmlinux`, a `.o`) nothing is left out and the output is as before. `--json` gives machine-readable output. On the GKI aarch64 `Image` from the [walkthrough](../README.md#try-it), `--raw` prints the totals of the [6.1 aarch64 table in VERIFICATION.md](VERIFICATION.md#kcfi-on-real-kernels) except for the 6 candidates in `.rodata` (11,961 sites with candidates and 1,694 with exactly one, against 11,960 and 1,695), in about a second of CPU time (0.8 to 2.1 s wall-clock on the machine named under that table, depending on its load).

Headless inside IDA, with idalib (cfiscope 0.1.17 or later; IDA 9.1 or newer; set up the `idapro` module as Hex-Rays describes):

```
python3 tools/cfiscope_headless.py vmlinux [--define-functions] [--remove] [--no-analysis]
```

It opens the file as a database, adds the same comments and cross-references as **CFIScope: Scan kCFI calls**, prints the same statistics and saves the database. Without `--define-functions` it is like answering No: a candidate inside a function IDA has gets a data cross-reference instead of a call cross-reference, and one IDA has no function for gets none. With `--no-analysis` IDA's auto-analysis, which creates the functions, does not run, so a fresh kernel file may have no functions yet: add `--define-functions` to get cross-references. It calls the plugin's own `cfiscope.idalayer`; like the rest of the IDA layer it has only been run against fake modules (`tests/test_headless_stub.py`), not a real idalib.
